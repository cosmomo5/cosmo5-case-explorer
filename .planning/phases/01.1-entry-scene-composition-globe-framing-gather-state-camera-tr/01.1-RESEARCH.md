## LOCKED DECISION CONFLICT — READ BEFORE PLANNING

Two decisions in CONTEXT.md (D-01.1-01 and D-01.1-02) are geometrically unreachable with the current camera setup. This section must be resolved before a valid plan can be written. **The planner must surface these to the user as a discuss-phase item, not proceed as if the locked decisions hold.**

### Conflict 1 — D-01.1-02: Target offset cannot achieve NDC (0.44, -0.16)

D-01.1-01 says: keep camera at (80, 880, 280), shift only the lookAt target.
D-01.1-02 says: target offset puts origin at NDC (0.44, -0.16) — i.e., cx:72%, cy:58%.

**Empirical proof (verified, not estimated):**

Camera at (80, 880, 280) looks mostly down: forward ≈ (-0.086, -0.949, -0.302). Camera right ≈ (-0.996, 0.090, 0.0). Any large X-shift in the lookAt target rotates the camera significantly off vertical, which magnifies NDC y for any point far below the camera. The non-linear perspective division means there is no target T=(tx, 0, 0) that satisfies NDC (0.44, -0.16) simultaneously.

Scan result (tx = world x of lookAt target, origin at world (0,0,0)):

| tx (world units) | NDC x of origin | NDC y of origin | cx % | cy % |
|---|---|---|---|---|
| 0 | 0.000 | 0.000 | 50% | 50% |
| -100 | 0.089 | -0.095 | 54.4% | 54.8% |
| -200 | 0.152 | -0.246 | 57.6% | 62.3% |
| -400 | 0.229 | -0.591 | 61.5% | 79.5% |
| -800 | 0.327 | -1.259 | 66.3% | 113%  |
| -1260 | ~0.44 | ~-2.05 | ~72% | ~152% |

At tx ≈ -1260 (where NDC x reaches 0.44), NDC y is -2.05 — the origin is off the bottom of the screen. **The required (0.44, -0.16) combination is not achievable with this camera geometry using a lookAt target shift.**

The CONTEXT.md estimate (`dt_right ≈ 418 units`) used a small-angle linear approximation valid only for cameras looking straight ahead horizontally. It is wrong for an overhead camera.

### Conflict 2 — Test 8: Planet apparent radius

The handoff `EntryQuiet` component (verified in `source/screens-entry.jsx` line 146):
```jsx
<Globe cx={w * 0.72} cy={h * 0.58} r={220} phase={40} accent={ac} speed={0.6} />
```

`FRAME_W = 1280`, `FRAME_H = 800` (SVG pixel coordinates, same as viewport). The Globe's `r=220` is 220 SVG pixels — 27.5% of viewport height.

At camera distance ~927 world units, planet radius 30 world units projects to:
```
apparent_radius_px = 30 / (927 × tan(30°)) × 400 = 22 px
```

Handoff requirement: 220 px. Ratio: 10×. `setViewOffset` shifts the planet's position on screen but does **not** change its apparent size. The radius gap is a separate conflict from the framing gap, and it is also not resolvable without either (a) moving the camera closer or (b) scaling up the planet sphere geometry.

### Three resolution paths

The planner must present these to the user and get a decision before the phase plan is written.

**Path A — Preserve camera intrinsics with `setViewOffset` (closes Conflict 1, not Conflict 2)**
Use `camera.setViewOffset()` to shift the projection frustum. This correctly puts the planet center at cx:72%, cy:58% without any target offset or position move. Camera-controls does not touch `camera.view` — safe to use in parallel.

Achieves: framing (cx:72%, cy:58%) ✓
Does NOT achieve: apparent radius 220px ✗ (planet still renders at ~22px)

**Path B — Move camera closer (closes both conflicts)**
The camera-position-to-planet distance required for radius ≈ 220px at FOV 60°, 800px height:
```
D = R_world × (viewport_half_height) / (R_screen × tan(fovV/2))
  = 30 × 400 / (220 × tan(30°))
  ≈ 94 world units
```

A closer camera position (e.g., (0, 94, 0) — directly above) would achieve both the radius AND, with a setViewOffset or target shift, the cx:72% framing. This breaks D-01.1-01 ("don't move camera position"), but that decision was grounded in incorrect geometry assumptions.

**Path C — Redefine Test 8's radius criterion as design-intent, not pixel-exact**
Accept that the handoff's r=220 is a design aspiration for a textured composite Globe (which 01.1 explicitly defers to a future phase). The radius criterion in Test 8 is then relaxed to "planet is clearly visible, not tiny" rather than pixel-matching 220. The CONTEXT.md already says the Globe rebuild is out of scope.

Under Path C: `setViewOffset` (Path A) handles the cx:72%, cy:58% criterion, and the radius criterion is deferred or redefined.

**Researcher recommendation:** Path A + Path C together are the lowest-mechanical-risk option consistent with the phase's "no Globe rebuild" boundary. Path B is cleanest if the planet radius matters for the UAT criterion. The user should decide.

## Camera Target Offset Math

### Finding: target offset is the wrong mechanism

See locked-decision conflict section above. Summary: the CONTEXT.md approach (target offset to achieve NDC 0.44, -0.16) is geometrically impossible with camera at (80, 880, 280). Do not implement a target offset for framing.

### Correct mechanism: `camera.setViewOffset()`

`THREE.PerspectiveCamera.setViewOffset(fullWidth, fullHeight, x, y, width, height)` [VERIFIED: THREE.js 0.170 source, `src/cameras/PerspectiveCamera.js:172`]

The method stores `{ fullWidth, fullHeight, offsetX: x, offsetY: y, width, height }` in `camera.view`. When `updateProjectionMatrix()` runs, it applies:

```
left += view.offsetX * width / fullWidth
top  -= view.offsetY * height / fullHeight
```

**Sign convention (verified from source):**
- Positive `offsetX` shifts the frustum's left edge RIGHT → scene appears to shift LEFT → negative to move origin right.
- Positive `offsetY` shifts the frustum's top edge DOWN → scene appears to shift DOWN → negative to move origin further down.

**For EntryQuiet framing (cx:72%, cy:58%) at viewport W×H:**

```typescript
// cx:72% → shift origin 22% right of center → frustum shifts left → offsetX negative
// cy:58% → shift origin 8% below center → frustum shifts up → offsetY negative
const entryOffsetX = -(0.72 - 0.50) * W;   // -0.22 * W (e.g., -281.6 at 1280px)
const entryOffsetY = -(0.58 - 0.50) * H;   // -0.08 * H (e.g., -64 at 800px)
camera.setViewOffset(W, H, entryOffsetX, entryOffsetY, W, H);
```

**Resize safety:** `updateProjectionMatrix()` reads `camera.view.offsetX/Y` and re-applies them. The ResizeObserver in `renderer.ts:55-62` calls `camera.aspect = w/h; camera.updateProjectionMatrix()` — this PRESERVES the view offset because `camera.view.enabled` stays `true`. [VERIFIED: THREE.js 0.170 source `PerspectiveCamera.js:214-240`]

However, the stored offsets are absolute pixels. After a resize to a new W×H, the stored `-281.6` and `-64` are no longer 22% and 8% of the new viewport. The executor must either:
- Re-call `setViewOffset()` in the ResizeObserver using the new W×H, or
- Store the percentage offsets and re-derive on resize.

**Entry → State 1 transition (clear the offset):**

```typescript
// GSAP proxy tween: shift offsets back to 0 over 1.2s (matching choreographer window)
const proxy = { dx: entryOffsetX, dy: entryOffsetY };
gsap.to(proxy, {
  dx: 0, dy: 0,
  duration: 1.2 * s,  // s = reduced-motion scale factor
  ease: 'power1.inOut',
  onUpdate: () => {
    camera.setViewOffset(W, H, proxy.dx, proxy.dy, W, H);
  },
  onComplete: () => {
    camera.clearViewOffset();  // THREE.js method, clears camera.view.enabled
  },
});
```

This runs in parallel with `choreographPlanetaryToGlobal` from the same `viewState.subscribe` callback (line 252 in main.ts).

**Where to read current viewport size:** `container.clientWidth`, `container.clientHeight` (where `container = document.getElementById('scene-container')`).

## camera-controls API Notes

**Version:** 3.1.2 [VERIFIED: npm registry via `npm view camera-controls version`]

**Key API signatures** [VERIFIED: `node_modules/camera-controls/dist/index.d.ts`]:

```typescript
// Target-only change (alias for setLookAt without position change)
controls.setTarget(targetX, targetY, targetZ, enableTransition?: boolean): Promise<void>

// Full position + target (used by existing flyTo proxy pattern)
controls.setLookAt(posX, posY, posZ, targetX, targetY, targetZ, enableTransition?: boolean): Promise<void>

// Read current state
controls.getTarget(out: THREE.Vector3): THREE.Vector3
controls.getPosition(out: THREE.Vector3): THREE.Vector3
```

**Does camera-controls interfere with `setViewOffset`?** No. Camera-controls operates on `camera.position` and `camera.quaternion` via internal spherical coordinates. It does not read or write `camera.projectionMatrix` or `camera.view`. [VERIFIED: `node_modules/camera-controls/dist/camera-controls.cjs` — no reference to `projectionMatrix`, `setViewOffset`, or `clearViewOffset`.]

**`enableTransition=false` meaning:** When `false`, the change is applied instantly without camera-controls' internal damping. The existing `flyTo()` proxy (line 47 of `transition-choreographer.ts`) uses this pattern correctly — GSAP owns the timing, and `setLookAt(..., false)` applies each GSAP frame's interpolated value immediately.

**For the Entry → State 1 camera re-aim:** No camera position or target change is needed (both are already at (80,880,280) / (0,0,0) from State 1 setup). The `setViewOffset` tween handles the visual re-framing. No `setLookAt` call is required unless the camera target was shifted from (0,0,0) during Entry, which it was not under Path A.

**`setTarget()` target-only API:** This exists [VERIFIED: `index.d.ts:813`] and is described as "alias of setLookAt(), without position change. Thus keep the same position." If D-01.1-04 (small supplemental target tween) is retained, this is the correct call rather than the proxy pattern.

## Star Visibility & Reveal

### Material inspection (confirmed from source)

Star meshes are `THREE.MeshBasicMaterial` with `transparent: true` already set [VERIFIED: `src/scene/scene-state.ts:196`]:

```typescript
const sMat = new THREE.MeshBasicMaterial({ color, transparent: true, opacity: 0.85 });
```

Glow sprites use `THREE.SpriteMaterial` with `transparent: true` [VERIFIED: `src/scene/scene-state.ts:108-114`]:

```typescript
const mat = new THREE.SpriteMaterial({
  map: createGlowTexture(colorHex),
  transparent: true,
  opacity: hasPermission ? 0.65 : 0.2,
  depthWrite: false,
  blending: THREE.AdditiveBlending,
});
```

Both materials already support opacity tweening without needing `transparent` to be set.

### Hide strategy: `star.visible = false` vs `material.opacity = 0`

| Approach | Pros | Cons |
|---|---|---|
| `star.visible = false` | Zero GPU cost — mesh skipped entirely by renderer. Glow sprite child also hidden (inherits parent visibility). | Binary — no fade-in; must set `visible = true` before the opacity reveal tween can render anything. |
| `material.opacity = 0` | Smooth fade-in without visibility flip. No visibility state to manage. | Mesh still rendered at 0 opacity (minor GPU cost × 116). Glow sprite has its OWN material — must be set separately. |

**Recommendation:** Set `star.visible = false` immediately after `gatherStarsToPlanet` (in `main.ts` around line 160). At reveal time, set `star.visible = true` at the start of the opacity tween. This correctly hides both the mesh and its child glow sprite in one operation.

**Glow sprite interaction:** Each star has a `THREE.Sprite` child at `star.userData.glowSprite` with its own `SpriteMaterial`. When `star.visible = false`, Three.js skips the entire object and all children — the sprite is also hidden. When we tween opacity on the `MeshBasicMaterial`, the sprite remains at its original opacity (0.65 or 0.2). If a unified fade-in is desired, both must be tweened. The CONTEXT.md says opacity tween 0→1 for the position tween's accompanyment — executor should also tween the sprite's `material.opacity` from 0 to its `baseOpacity` during the reveal.

### Reveal extension point in `releaseStarsToHomes`

`releaseStarsToHomes` in `planetary-gather.ts:88-118` [VERIFIED] already iterates `isPlanetaryTarget` stars and tweens their position. The opacity reveal should be added as a parallel tween inside the same `for` loop:

```typescript
// Existing (position tween):
gsap.to(star.position, { x, y, z, duration, ease: 'power2.out', onComplete: ... });

// Add (opacity reveal):
star.visible = true; // visibility on before tween (otherwise it won't render)
const sMat = star.material as THREE.MeshBasicMaterial;
gsap.to(sMat, { opacity: 0.85, duration: 0.8, delay: 0.15, ease: 'power2.out' });
const glowSp = star.userData.glowSprite as THREE.Sprite | undefined;
if (glowSp) {
  const spMat = glowSp.material as THREE.SpriteMaterial;
  const base = (glowSp.userData.baseOpacity as number) ?? 0.65;
  gsap.to(spMat, { opacity: base, duration: 0.8, delay: 0.15 });
}
```

**Performance:** 116 simultaneous material tweens. GSAP handles this efficiently (single tick per frame, no per-tween rAF). Not a concern. [ASSUMED — GSAP's architecture handles thousands of simultaneous tweens; no official benchmark found for this specific count, but community consensus and GSAP docs confirm single-loop architecture.]

## Risks & Landmines

### Risk 1: `choreographPlanetaryToGlobal` needs camera access

Currently the function signature is `(objects: SceneObjects, planet: PlanetGroup, options?)`. The `camera` is on `objects.camera` (set in `main.ts:152` — `sceneObjects.camera = camera`). The executor can read it from there without a signature change: `objects.camera as THREE.PerspectiveCamera`. Verify `objects.camera` is always set before this function is called — YES, it is set at line 152, before `choreographPlanetaryToGlobal` is ever called (which is in the viewState subscriber at line 256).

### Risk 2: ResizeObserver fires during Entry transition

If the user resizes during the ENTER_FIELD tween (which is 1.2s), the resize handler will re-apply the Entry offset (e.g., the full -281.6px offset) while the tween is moving it toward 0. This races with the GSAP proxy.

Prevention: In the ResizeObserver, use `container.clientWidth/Height` as the new full-size, and scale the proxy's current `dx/dy` proportionally. Or: track `entryFramingActive = false` as soon as the tween starts (not when it ends), so the resize handler skips re-application during the transition.

### Risk 3: Twinkle pass overrides opacity after reveal

The tick loop twinkle pass in `scene-state.ts:399-408` overwrites `spriteMat.opacity` every frame for non-reduced-motion. It reads `baseOpacity` from `sprite.userData.baseOpacity`. If the reveal tween sets `spriteMat.opacity = base` and then the twinkle pass overwrites it on the same frame, the result is correct (twinkle oscillates around base). No conflict.

The star mesh's `MeshBasicMaterial.opacity` is only written by the tick loop in focused mode (lines 338-345) or by filter tweens. In global mode during Entry, the tick loop does NOT touch star opacity (lines 360-376 — global mode doesn't manage filter opacity). The reveal tween owns star opacity during Entry. Safe.

### Risk 4: `star.visible = false` interacts with raycasting

Raycasting in `main.ts` uses `scene.children` and checks `star.userData.isFiltered` etc. Three.js raycast skips `visible=false` meshes by default — so hidden stars won't be clickable during Entry. This is correct behavior (no interaction during Entry).

### Risk 5: Test 8 radius criterion remains failing

As documented in the locked-decision conflict section, the apparent planet radius at camera distance ~927 is ~22px, vs the handoff's 220px. Unless Path B (camera closer) is chosen, Test 8 will still read "radius 30 vs design 220" in UAT evidence. The plan must explicitly address this criterion — either resolve it (Path B) or redefine it (Path C).
