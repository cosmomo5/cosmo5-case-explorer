<decisions>
## Implementation Decisions

### Camera framing mechanism (locked, revised 2026-04-25 post-research)
- **D-01.1-01 (REVISED):** Use **`camera.setViewOffset()`** to shift the projection frustum during Entry. Camera position stays at `(80, 880, 280)`. Camera target stays at `(0,0,0)`. Neither position nor lookAt is changed; only the projection frustum is offset.
  - **Why not the original target-shift plan?** Verified geometrically impossible. With camera at (80, 880, 280) looking mostly down (forward ≈ (-0.086, -0.949, -0.302)), any large X-shift in the lookAt target rotates the view off-vertical and blows out NDC y. At `tx=-1260` (where NDC x reaches 0.44), NDC y is -2.05 (off the bottom). See `01.1-RESEARCH.md` Conflict 1 for the verified scan. Target-shift cannot reach NDC (0.44, -0.16).
  - **Why setViewOffset works:** It manipulates the projection matrix directly — `left += view.offsetX * width / fullWidth`, `top -= view.offsetY * height / fullHeight`. Camera-controls v3.1.2 does not touch `camera.view`; safe to use in parallel. THREE.js source verified.

### Entry camera offset values (locked, revised)
- **D-01.1-02 (REVISED):** Use percentage-based viewport offsets:
  ```
  entryOffsetX = -(0.72 - 0.50) * W  =  -0.22 * W
  entryOffsetY = -(0.58 - 0.50) * H  =  -0.08 * H
  camera.setViewOffset(W, H, entryOffsetX, entryOffsetY, W, H)
  ```
  Where `W = container.clientWidth`, `H = container.clientHeight`. The offsets are recomputed on every resize (ResizeObserver re-applies them while Entry is active).

### Test 8 radius criterion (locked, redefined per Path C)
- **D-01.1-07 (NEW):** The handoff's Globe `r=220` is a design aspiration for a textured composite Globe (gravity wells + inclined orbital particles + atmospheric edge). At State 1 camera distance ~927 world units, the actual planet sphere (radius 30 world units) projects to ~22px — a 10× gap. **This phase does NOT close that gap.** Test 8's radius criterion is **redefined**: "planet renders clearly visible (apparent radius ≥ 18px at 1280×800), not pixel-matched to handoff's 220px." Closing the radius gap requires either moving the camera closer (out of scope — would force a "zoom out" tween into the choreographer) or rebuilding the planet as a textured composite (deferred to a future polish phase). The cx/cy framing criterion (72%/58% ± 4%) is unchanged and IS closed by this phase.

### Case-star visibility during Entry (locked)
- **D-01.1-03:** All 116 case-star sprites are **hidden** during Entry (`star.visible = false` or material opacity 0). They are revealed via the existing `releaseStarsToHomes` tween inside `choreographPlanetaryToGlobal` — the tween already starts at `t = 0.2s × s` and runs 1.2s, which is the on-stage reveal moment. Reveal is implemented as a sprite opacity tween from 0 → 1 starting at `t = 0.4s` with duration 0.8s (overlaps the existing position tween so stars fade in *while* migrating to their orbital homes).
  - **Why not particle-texture the planet surface?** That's a Globe rebuild, not a scope-fix. Hiding aligns with the existing `isPlanetaryTarget` flag semantics — the flag already gates tick-loop control of these stars during Entry.
  - **Why not tune positions/scales?** Fragile — handoff's "field of free galactic particles inside" is an aesthetic that depends on the underlying sphere being a textured composite. We can't fake it with billboard sprites without it looking like the current bug.

### Camera-transition timing on ENTER_FIELD (locked, revised)
- **D-01.1-04 (REVISED):** The Entry → State 1 camera transition runs as a **viewport-offset clear**: tween `(dx, dy)` from `(entryOffsetX, entryOffsetY)` → `(0, 0)` over duration `1.2 * s` (where `s = prefersReduced ? 0.33 : 1.0`), ease `power1.inOut`. Each tween frame calls `camera.setViewOffset(W, H, dx, dy, W, H)` via GSAP's `onUpdate`. On `onComplete`, call `camera.clearViewOffset()` to fully restore the projection. The tween is fired from inside `choreographPlanetaryToGlobal` (it accesses the camera via `objects.camera`) so it runs in parallel with the existing planet-fade / star-release sequence.
  - This means: at Entry → State 1 transition start, three things tween in parallel:
    1. Planet sphere fades out (existing, `choreographPlanetaryToGlobal` step 1+4)
    2. Stars migrate from sphere surface → orbital homes (existing, `releaseStarsToHomes`) AND fade in opacity 0 → base (NEW)
    3. Projection-frustum offset clears toward 0 (NEW in this phase)

### Files in scope (locked, revised)
- **D-01.1-05 (REVISED):** Files modified by this phase:

## Existing Code Insights

### Reusable Assets
- `THREE.PerspectiveCamera.setViewOffset(fullWidth, fullHeight, x, y, width, height)` and `clearViewOffset()` — built-in projection-frustum offset. Verified safe alongside `camera-controls` v3.1.2 (which does not touch `camera.view`).
- GSAP proxy pattern (see existing `flyTo()` lines 24–52 of `transition-choreographer.ts`) — model for the new offset-clearing tween. Animate a plain `{dx, dy}` object; apply via `setViewOffset` in `onUpdate`.
- `gatherStarsToPlanet()` already sets `userData.isPlanetaryTarget = true` per star. The visibility gate hooks this flag.
- `releaseStarsToHomes()` already iterates planetary-target stars during the choreographer. Extend the same iteration to set `visible = true` and tween material opacity.

### Established Patterns
- Camera control: `camera-controls` library handles position/lookAt; **`camera.setViewOffset` is independent of camera-controls** and must be used directly on the THREE camera object.
- GSAP proxies for camera tweens — never tween THREE objects directly. Apply each frame's interpolated value via the appropriate THREE / camera-controls method in `onUpdate`.
- Reduced-motion scaling: `s = prefersReduced ? 0.33 : 1.0`. Applied to durations, not to whether tweens fire.

### Integration Points
- Boot sequence in `main.ts`: createRenderer (line ~112) → buildOrbitalScene (line ~150) → createPlanet (line ~159) → gatherStarsToPlanet (line ~160) → mountCalibrationOverture (line ~164). <specifics>
## Specific Ideas

- The setViewOffset formula for cx:72%, cy:58%: `offsetX = -(0.72 - 0.50) * W = -0.22*W`, `offsetY = -(0.58 - 0.50) * H = -0.08*H`. Sign convention verified from THREE.js 0.170 source (`PerspectiveCamera.js:172`): positive `offsetX` shifts the frustum's left edge right → scene shifts left → negative offset moves the origin right. Same logic for Y.
- For visibility hide: set `star.visible = false` AND `material.opacity = 0` AND `glowSprite.material.opacity = 0` — three writes per star. The visibility flip is the primary gate; the opacity zeroing makes the reveal tween's starting state explicit. Star materials already have `transparent: true` (verified at `scene-state.ts:196`).
- For reveal: in `releaseStarsToHomes`, set `star.visible = true` first, then `gsap.to(material, { opacity: 0.85, duration, ... })` alongside the existing position tween. The glow sprite's `userData.baseOpacity` is the target for its own opacity tween.
- The tick-loop twinkle pass at `scene-state.ts:399–408` re-writes glow-sprite opacity each frame around `baseOpacity`; the reveal tween sets `baseOpacity` itself to a tweenable value (or tweens directly while twinkle is paused — researcher confirmed no conflict in global mode).

</specifics>
